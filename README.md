# Flutter-пайплайн для Claude Code

Скилл `/pipeline` для разработки Flutter-приложений с Claude Code. Он лечит три
типичные проблемы работы с агентом: Claude забегает вперёд и пишет код раньше, чем
договорились, что строим; теряет контекст между сессиями; и с одинаковой уверенностью
говорит «готово» про то, что проверил, и про то, что просто выглядит правильно.

## Происхождение

Основан на скилле `pipeline` из [claude-code-skills](https://github.com/Magerko/claude-code-skills)
автора magerdev ([@magerdev1](https://t.me/magerdev1)), распространяемом по лицензии MIT.

Что изменено относительно оригинала:

- пайплайн переделан под Flutter (iOS, Android, Web): своя архитектура и обязательные пакеты
  в `references/architecture.md`;
- разработка в две фазы — сначала UI на фейковых данных, затем бэкенд и API;
- реализация по TDD, работу функционала и UI проверяет человек вручную;
- генерацию запускает агент, сгенерированные файлы в git не хранятся (шаблон `.gitignore` —
  в `architecture.md`);
- стиль: dot shorthands, один файл — один класс; настройки — в `shared_preferences`;
  логи всех пакетов и навигации на всех уровнях — через Talker;
- убраны стадия выката и скиллы `launch-web` и `launch-security`;
- макет как строгий образец или как ориентир;
- правила для проекта, где код уже есть: фаза по изменению, старый код не переделывается
  без просьбы, базовая точка анализатора и тестов;
- скилл запускается только вручную.

Автор изменений: [xXxogan](https://github.com/xXxogan).

## Что внутри

### `/pipeline` — Flutter-приложение от идеи до проверенного кода

Ведёт проект по десяти стадиям с жёсткими воротами между ними: идея → план
с критериями приёмки → risk spikes → контракты → сквозной слайс → задачи → реализация →
аудит → фидбек. Приложение строится в две фазы: сначала весь UI на фейковых данных
(фундамент — тема, навигация, локализация, DI, логи — первым делом), затем бэкенд и API.
Идею и вид приложения (макет, цвета, шрифты) Claude выясняет вопросами на первой стадии;
идею можно сразу передать аргументом: `/pipeline <что строим>`. Макет можно дать как строгий
образец или как ориентир по экранам и функционалу. Реализация — по TDD, а работу функционала
и UI я проверяю сам по командам и шагам, которые даёт Claude. Каждая стадия материализуется в файл в `docs/pipeline/` (в git
он не хранится), и после каждой Claude останавливается и спрашивает разрешение идти дальше.

Смысл в двух вещах. Первая: файлы, а не контекст. Сессия умирает, `docs/pipeline/` живёт —
новая сессия поднимает проект с той же точки, а не с моего пересказа. Вторая: ворота.
Именно они не дают модели написать реализацию, пока мы ещё обсуждаем, что вообще строим —
самая дорогая ошибка при работе с ИИ-агентом.

Аудит своего же кода скилл отдаёт отдельному субагенту со свежим контекстом: тот не видел,
как код писался, и в этом весь смысл — он проверяет критерии приёмки запуском, а не чтением.

## Установка

Windows:

```powershell
.\install.ps1
.\install.ps1 -DryRun
```

macOS / Linux:

```bash
chmod +x install.sh
./install.sh
./install.sh --dry-run
```

Скрипт копирует `skills/` и `agents/` в `~/.claude/`, перезаписывая одноимённые папки.
Остальное содержимое `~/.claude` не трогается. Изменения подхватываются в новой сессии
Claude Code — проверить можно, набрав `/` и посмотрев список.

Если Windows ругается на запуск скрипта, снимите блокировку скачанного файла:

```powershell
Unblock-File .\install.ps1
powershell -ExecutionPolicy Bypass -File .\install.ps1
```

Не хотите ставить глобально — скопируйте `skills/pipeline` в `.claude/skills/`
внутри конкретного проекта, тогда скилл будет виден только там (субагенты из `agents/` — в `.claude/agents/`).

Эта папка — источник правды. Правьте здесь и запускайте установку заново; файлы
в `~/.claude/skills` руками не трогайте, они перезапишутся.

## Кто и когда запускает

Только вручную: `/pipeline`, можно с номером стадии — `/pipeline 4`. Сам Claude скилл
не запускает: во фронтматтере стоит `disable-model-invocation: true`, поэтому он не
подгружается ни по смыслу разговора, ни в субагентах, ни по расписанию.

## Что стоит поправить под себя

- `pipeline/references/architecture.md` — моя архитектура Flutter-приложения и обязательный
  набор пакетов. Скилл считает его законом, так что под свой проект правьте в первую очередь его.
- Раздел «Стиль кода» в `pipeline/SKILL.md` — мой. Правила про комментарии там довольно
  жёсткие, и это осознанно, но вкусы у всех разные.
- `pipeline` требует подтверждения на каждых воротах. Если это раздражает, скажите
  «не спрашивай, гони до конца» — скилл это понимает.

## Заметки по фронтматтеру

Собрал по документации:

- `allowed-tools` — это **пред-одобрение** (меньше запросов на подтверждение), а не
  ограничение. Ограничивает `disallowed-tools`. Оба сбрасываются со следующим сообщением.
- `disable-model-invocation: true` — скилл не подгружается автоматически, не
  предзагружается в субагентов и не срабатывает по расписанию.
- `user-invocable: false` — обратное: скрыть из меню `/`, оставить только автозагрузку.
- `context: fork` — выполнение в отдельном субагенте, основной контекст не засоряется.
- `model` и `effort` можно прибить к скиллу — например `effort: high`.
