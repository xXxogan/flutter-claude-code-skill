# Чек-лист безопасности перед выкаткой

У каждого пункта: **приоритет**, **проверка** — чем именно подтверждается, **ловушка** —
как этот пункт обычно проваливают, считая закрытым.

Секции: `secrets` (A) · `auth` (B) · `access` (C) · `input` (D) · `files` (E) ·
`headers` (F) · `limits` (G) · `leaks` (H) · `deps` (I) · `prod` (J) · `money` (K) · `ai` (L)

Команды grep даны для ориентира — адаптируй под язык и структуру проекта.

---

## A. Секреты и конфигурация — `secrets`

**SEC-01 · В коде нет секретов** — P1
Проверка: `grep -rnE "(sk-[a-zA-Z0-9]{16,}|AKIA[0-9A-Z]{16}|service_role|BEGIN (RSA|OPENSSH) PRIVATE KEY|password\s*=\s*[\"'][^\"']{6,})" --include="*.{ts,tsx,js,jsx,py,go,rb,php,java,yml,yaml,json,env*}" .`
Плюс прогон gitleaks/trufflehog, если доступны.
Ловушка: ключ «спрятали» в отдельный файл конфига, который лежит в репозитории.

**SEC-02 · История git чиста, ключи ротированы** — P1 · 🙋
Проверка: `git log --all -p -S "<фрагмент ключа>" | head` — секрет встречался в истории?
Порядок действий строго такой: **1) отозвать и перевыпустить ключ у провайдера,
2) только потом чистить историю** (`git filter-repo`, BFG).
Ловушка, из-за которой пункт бесполезен: переписывание истории **не удаляет** секрет из
форков, из открытых PR, из кэша GitHub и у всех, кто уже клонировал репозиторий.
Ключ, побывавший в репозитории, считается скомпрометированным навсегда. Force-push
переписанной истории ломает ветки у всей команды — предупреди об этом до, а не после.

**SEC-03 · .env не в репозитории** — P1
Проверка: `git ls-files | grep -E "^\.env"` — пусто. `.gitignore` содержит `.env*`,
кроме `.env.example`. В `.env.example` — только имена переменных, без значений.

**SEC-04 · Во фронтенд-бандл не утекли приватные ключи** — P1
Проверка: переменные с префиксом `NEXT_PUBLIC_`, `VITE_`, `REACT_APP_`, `PUBLIC_`
**по определению попадают в браузер**. Просмотри их список. Затем грепни собранный бандл:
`grep -rE "sk-|service_role|secret" dist/ build/ .next/static/ 2>/dev/null | head`.
Ловушка: `NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY` — встречается регулярно и означает полный
доступ к базе у любого посетителя сайта.

**SEC-05 · Секреты прода приходят из секрет-стора** — P2
Проверка: переменные окружения хостинга/секрет-менеджера, а не файл в образе и не хардкод
в CI-конфиге. В логах сборки секреты не печатаются.

**SEC-06 · Dev и prod разделены** — P1
Проверка: разные ключи и разные базы. Локальная разработка не подключена к прод-БД.
Тестовые платёжные ключи не уехали в прод и наоборот.
Ловушка: один `DATABASE_URL` на всё — миграция или сид на локалке чистит прод.

## B. Аутентификация и сессии — `auth`

**SEC-07 · Пароли хешируются нормальным алгоритмом** — P1
Проверка: argon2id или bcrypt (cost ≥ 10) или scrypt. Найди место хеширования и алгоритм.
Ловушка: SHA-256/MD5 «с солью», самописная схема, шифрование вместо хеширования.
Отдельно рассмотри вариант вообще не хранить пароли: OAuth или magic link.

**SEC-08 · Авторизация проверяется на сервере при каждом запросе** — P1
Проверка: пройди по всем роутам/эндпоинтам и найди проверку сессии. Скрытая в UI кнопка
и редирект в роутере — не защита.
Ловушка (Next.js): `middleware.ts` не покрывает route handlers, server actions и статически
сгенерированные пути. Проверка нужна внутри каждого обработчика.

**SEC-09 · Cookies сессии настроены** — P1
Проверка: `HttpOnly`, `Secure`, `SameSite=Lax` (или `Strict`), разумный срок жизни, `Path=/`.
Ловушка: токен в `localStorage` — доступен любому XSS.

**SEC-10 · Сессии отзываются** — P2
Проверка: смена пароля, выход и блокировка пользователя инвалидируют существующие сессии.
Для JWT: короткий TTL access-токена + ротация refresh-токена + список отозванных.
Ловушка: stateless JWT на 30 дней невозможно отозвать — угнанный токен живёт месяц.

**SEC-11 · Восстановление пароля безопасно** — P1
Проверка: одноразовый токен с коротким сроком, привязан к пользователю, инвалидируется
после использования, не пишется в логи, не передаётся в URL, который потом уходит в Referer.

**SEC-12 · Нет перечисления пользователей** — P2
Проверка: логин, регистрация и сброс пароля отвечают одинаково для существующего
и несуществующего email («если такой адрес есть, мы отправили письмо»).
Ловушка: разные тексты ошибок или заметно разное время ответа выдают базу пользователей.

**SEC-13 · Чувствительные действия защищены дополнительно** — P2
Проверка: смена email/пароля, вывод средств, удаление аккаунта требуют текущий пароль
или повторную аутентификацию.

**SEC-14 · Регистрация не открыта для мусора** — P3
Проверка: подтверждение email, запрет одноразовых доменов при необходимости, лимит
регистраций с одного IP.

## C. Авторизация и доступ к данным — `access`

Здесь живёт уязвимость №1 быстро собранных приложений. Проверяй по одному эндпоинту,
не «в целом».

**SEC-15 · Нет IDOR / BOLA** — P1
Проверка: для каждого эндпоинта, принимающего идентификатор (`/api/orders/:id`,
`?userId=`, `documentId` в теле), в коде должна быть проверка **владения или права**,
а не только аутентификации. Составь таблицу: эндпоинт → где проверяется владение.
Активная проверка (с разрешения, на стенде): войти как A, подставить `id` объекта B.
Ожидаемо `403/404`, а не `200`.
Ловушка: `SELECT * FROM orders WHERE id = $1` без `AND user_id = $2`. Проверка «пользователь
залогинен» присутствует, и пункт кажется закрытым.

**SEC-16 · Роли проверяются на сервере** — P1
Проверка: права берутся из БД или из подписанного токена **с проверкой подписи**, а не из
поля в теле запроса и не из клиентского состояния.

**SEC-17 · Нет массового присвоения полей** — P1
Проверка: тело запроса не разворачивается в модель целиком (`{...req.body}`, `Model(**data)`,
`update(req.body)`). Явный whitelist полей.
Ловушка: пользователь дописывает в JSON `"role":"admin"`, `"balance":100000`, `"price":1`,
`"isVerified":true` — и это сохраняется.

**SEC-18 · RLS/правила доступа включены и проверены** — P1 (Supabase/Firebase)
Проверка: RLS включён на **каждой** таблице с пользовательскими данными, и у каждой есть
политики на select/insert/update/delete. Прочитай тексты политик.
Активная проверка: анонимным (публичным) ключом запросить чужую строку — должно вернуть пусто.
Ловушка №1: RLS включён, политик нет — приложение молча перестаёт видеть данные, и это
«чинят» политикой `using (true)`, которая открывает таблицу всем.
Ловушка №2: галочка «RLS enabled» в дашборде проверена, тексты политик — нет. Галочка
ничего не гарантирует.

**SEC-19 · service_role / admin SDK только на сервере** — P1
Проверка: сервисный ключ Supabase, Firebase Admin SDK, ключ БД не встречаются во фронтовом
коде и в бандле. Во фронте — только анонимный/публичный ключ, который безопасен **лишь**
при работающем RLS (см. SEC-18).

**SEC-20 · Списки и поиск тоже фильтруются** — P1
Проверка: `GET /api/orders`, поиск, экспорт, отчёты фильтруют по владельцу. Не только
детальный эндпоинт.
Ловушка: детальный доступ закрыли, а список отдаёт всё — с пагинацией, что удобнее для выгрузки.

**SEC-21 · Хранилище файлов не публичное по умолчанию** — P1
Проверка: бакеты приватные, доступ через signed URL с коротким TTL, права на запись
ограничены владельцем.
Ловушка: публичный бакет с «непредсказуемыми» именами файлов. Имена перебираются,
листинг часто открыт.

## D. Ввод, инъекции, вывод — `input`

**SEC-22 · Запросы параметризованы** — P1
Проверка: `grep -rnE "(query|execute|raw)\(.*\$\{|\+ *(req|request)\.|f\"SELECT|% *\(" src/`
ORM не индульгенция: смотри `raw`, `queryRaw`, `extra`, динамические `ORDER BY`/имена таблиц,
которые нельзя параметризовать — их только по whitelist.
Ловушка: `LIKE '%${q}%'` и сортировка по полю из query-строки.

**SEC-23 · Ввод валидируется на сервере схемой** — P1
Проверка: zod/pydantic/joi/схема фреймворка на каждом эндпоинте; whitelist допустимых
значений, лимит длины строк и размера тела запроса.
Ловушка: клиентская валидация принимается за валидацию. Запрос уходит мимо браузера.

**SEC-24 · Нет XSS** — P1
Проверка: `grep -rnE "dangerouslySetInnerHTML|v-html|innerHTML|outerHTML|mark_safe|html_safe|\|safe" src/`
Каждое вхождение — либо доверенный источник, либо санитизация (DOMPurify) на сервере.
Ловушка: «мы же экранируем на входе» — экранировать нужно на выводе, под конкретный контекст
(HTML, атрибут, URL, JS). Ручное экранирование почти всегда неполно; полагайся на фреймворк.

**SEC-25 · CSP настроена** — P2
Проверка: заголовок `Content-Security-Policy` есть и осмысленный (не `unsafe-inline` на всё).
Порядок внедрения: сначала `Content-Security-Policy-Report-Only` и наблюдение, потом enforce.
Ловушка: включённая сразу строгая CSP ломает аналитику, виджеты и часть своих скриптов —
и её снимают целиком вместо настройки.

**SEC-26 · Нет SSRF** — P1, если сервер ходит по URL пользователя
Проверка: импорт по ссылке, превью URL, вебхуки наружу, загрузка аватара по адресу.
Нужен whitelist схем (`http/https`), запрет приватных диапазонов (`127.0.0.0/8`, `10/8`,
`172.16/12`, `192.168/16`, `::1`) и **особенно** `169.254.169.254` — метаданные облака,
откуда забирают ключи. Редиректы проверять после каждого перехода, а не только первый URL.

**SEC-27 · Нет обхода пути** — P1, если файлы читаются по имени из запроса
Проверка: имя файла из запроса не подставляется в путь. Нормализация + проверка, что
итоговый путь внутри разрешённой директории.
Ловушка: фильтрация `../` строкой обходится кодированием.

**SEC-28 · Нет инъекции команд ОС** — P1
Проверка: `exec`, `spawn(..., {shell:true})`, `os.system`, `subprocess` со строкой.
Аргументы передавать массивом, без shell.

## E. Загрузка файлов — `files`

**SEC-29 · Тип определяется по содержимому** — P1
Проверка: magic bytes / sniffing на сервере, а не расширение и не `Content-Type` из запроса —
и то и другое подделывается тривиально. Whitelist форматов, не blacklist.

**SEC-30 · Есть лимиты** — P2
Проверка: максимальный размер файла и общий объём на пользователя, ограничение количества,
таймаут загрузки. Иначе загрузка — это и есть DoS.

**SEC-31 · Файлы отдаются безопасно** — P1
Проверка: отдача с отдельного домена или из бакета (не с основного домена приложения —
иначе загруженный HTML/SVG исполняется в контексте вашего домена и крадёт сессию),
`Content-Disposition: attachment` где уместно, `X-Content-Type-Options: nosniff`,
исполнение в директории загрузок запрещено.
Ловушка: SVG считают картинкой. SVG — это документ со скриптами.

## F. Транспорт, заголовки, CORS — `headers`

**SEC-32 · HTTPS принудительно** — P1
Проверка: весь http редиректится на https, нет mixed content, сертификат автопродлевается.

**SEC-33 · HSTS** — P2
Проверка: `Strict-Transport-Security` с разумным `max-age`.
Ловушка: `preload` — **решение почти необратимое** (удаление из списка браузеров занимает
месяцы). Не включай preload на новом домене, пока https не работает стабильно на всех
поддоменах. Начинай с небольшого `max-age` и увеличивай.

**SEC-34 · Базовые заголовки** — P3
Проверка: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` или
`frame-ancestors 'none'` в CSP, `Referrer-Policy: strict-origin-when-cross-origin`,
`Permissions-Policy` для неиспользуемых API. Уберите заголовки, раскрывающие версии
(`X-Powered-By`, `Server`).

**SEC-35 · CORS настроен явно** — P1
Проверка: список разрешённых origin, а не отражение `Origin` из запроса.
Ловушка: `Access-Control-Allow-Origin: *` вместе с `Allow-Credentials: true` — это либо
не работает, либо (при отражении origin) означает, что любой сайт делает запросы от имени
залогиненного пользователя. Отражение origin — самая частая «рабочая» реализация CORS.

**SEC-36 · CSRF закрыт** — P2
Проверка: для форм и cookie-аутентификации — CSRF-токен или строгая проверка origin.
Ловушка: `SameSite=Lax` считают достаточным. Он не покрывает GET-запросы с побочными
эффектами и часть сценариев с поддоменами.

## G. Лимиты, боты, расходы — `limits`

**SEC-37 · Rate limit на чувствительных эндпоинтах** — P1
Проверка: логин, регистрация, сброс пароля, отправка OTP/SMS, отправка формы — ограничены
по IP и по аккаунту, с прогрессивной задержкой или блокировкой.
Ловушка: лимит только на логине. Перебор идёт через сброс пароля и OTP, где ещё и деньги
за SMS тратятся.

**SEC-38 · Лимит на дорогие операции** — P1, если есть платные вызовы
Проверка: эндпоинты, дергающие LLM, генерацию изображений, SMS, email, — квота на
пользователя и глобальный потолок.
Ловушка: бесплатный публичный эндпоинт с вызовом LLM — сегодня самый быстрый способ
получить счёт на тысячи долларов за ночь. Атака выглядит как обычный трафик.

**SEC-39 · Лимиты трат и алерты у провайдеров** — P1 · 🙋
Проверка: биллинг-алерты и жёсткие лимиты в облаке, у LLM-провайдера, у SMS-шлюза.
Это единственная защита, которая работает, когда все остальные не сработали.

**SEC-40 · Бот-защита на публичных формах** — P2
Проверка: Turnstile/hCaptcha в невидимом режиме, honeypot, проверка на сервере.
Ловушка: картиночная CAPTCHA бьёт по конверсии и доступности сильнее, чем боты.

**SEC-41 · Нет гонок при списании** — P2
Проверка: изменение баланса, квоты, остатка товара — атомарной операцией БД или
транзакцией с блокировкой, а не «прочитал, посчитал, записал».
Ловушка: параллельные запросы на списание одной и той же квоты проходят оба.

## H. Утечки данных и логи — `leaks`

**SEC-42 · API отдаёт только нужные поля** — P1
Проверка: сериализаторы возвращают whitelist полей. Грепни ответы на `password`,
`password_hash`, `token`, `email` в списках чужих пользователей, внутренние комментарии,
служебные флаги.
Ловушка: `SELECT *` → `res.json(user)`. На фронте лишние поля не видны, в DevTools — видны.

**SEC-43 · В проде нет отладочной информации** — P1
Проверка: `DEBUG=false`, стектрейсы не уходят клиенту, ошибки наружу — обобщённые,
детали — в лог. Source maps не публикуются (или ограничены).
Ловушка: страница ошибки Django/Flask/Next в dev-режиме показывает переменные окружения.

**SEC-44 · В логах нет секретов и ПД** — P2
Проверка: не логируются пароли, токены, тела запросов авторизации, номера карт,
полные ПД. Особенно — тела вебхуков и запросов к платёжкам.

**SEC-45 · Есть аудит-лог значимых действий** — P2
Проверка: кто, что, когда — вход, смена прав, удаление, финансовые операции.
Без этого инцидент невозможно расследовать даже постфактум.

**SEC-46 · Мониторинг и алерты** — P2
Проверка: всплеск 401/403/500, аномальный трафик, ошибки в Sentry-подобном сервисе
доходят до человека.

## I. Зависимости — `deps`

**SEC-47 · Lockfile закоммичен, аудит в CI** — P2
Проверка: `package-lock.json`/`poetry.lock`/`go.sum` в репозитории; `npm audit`,
`pip-audit`, Dependabot включены.
Ловушка: `npm audit fix --force` поднимает мажорные версии и ломает сборку. Правь адресно.

**SEC-48 · Незнакомые пакеты проверены** — P2
Проверка: свежедобавленные зависимости — реальные, популярные, без опечаток в имени
(typosquatting), без подозрительных `postinstall`-скриптов.

**SEC-49 · Рантайм и базовые образы не EOL** — P3
Проверка: версии Node/Python/PHP/образов получают обновления безопасности.

## J. Прод-гигиена — `prod`

**SEC-50 · Убраны тестовые данные и учётки** — P1
Проверка: сид-пользователи, `admin/admin`, демо-аккаунты, тестовые платежи, моковые данные
не поехали в прод.

**SEC-51 · Закрыты служебные интерфейсы** — P1
Проверка: `/debug`, `/admin` без авторизации, Swagger/GraphQL Playground в проде,
Adminer/phpMyAdmin, открытые дашборды очередей и метрик, `.git/` доступный по HTTP
(`curl -sI <url>/.git/config`).

**SEC-52 · Бэкапы есть и восстановление проверено** — P1 · 🙋
Проверка: автоматические бэкапы БД и файлов, известна периодичность и срок хранения,
**восстановление хотя бы раз выполнено**.
Ловушка: бэкапы лежат в том же аккаунте/бакете, что и прод, или сам бакет публичный.

**SEC-53 · Миграции и доступ к прод-БД под контролем** — P2
Проверка: миграции применяются из CI, а не руками с ноутбука; прямой доступ к прод-БД
ограничен списком IP; есть учёт, у кого есть доступы.

**SEC-54 · План на инцидент** — P3 · 🙋
Проверка: понятно, как отозвать все сессии, отключить фичу, перевыпустить ключи, кому
писать. Одна страница текста, не регламент.

## K. Платежи и вебхуки — `money`

**SEC-55 · Сумма считается на сервере** — P1
Проверка: цена, скидка, итог берутся из БД по идентификаторам товаров. Из клиента приходят
только `id` и количество.
Ловушка: `amount` в теле запроса. Самый воспроизводимый баг платного продукта.

**SEC-56 · Подпись вебхука проверяется** — P1
Проверка: проверка подписи провайдера (Stripe/ЮKassa/др.) на **сыром** теле запроса
до парсинга JSON, сравнение в постоянном времени.
Ловушка: middleware парсит и пересобирает JSON — подпись перестаёт сходиться, и проверку
«временно» отключают.

**SEC-57 · Обработка вебхуков идемпотентна** — P2
Проверка: повторная доставка того же события не начисляет второй раз. Ключ события
сохраняется.
Ловушка: повторы — штатное поведение платёжных систем, а не сбой.

**SEC-58 · Карточные данные не проходят через ваш сервер** — P1
Проверка: используется виджет/редирект провайдера. Номера карт не попадают в ваш код,
логи и БД ни при каких условиях.

**SEC-59 · Статус заказа меняет только подтверждённый платёж** — P1
Проверка: заказ переходит в «оплачен» по вебхуку/серверной сверке, а не по редиректу
пользователя на success-страницу.
Ловушка: success-URL открывается вручную — заказ оплачен без оплаты.

## L. Если внутри LLM — `ai`

**SEC-60 · Ключ провайдера только на сервере** — P1
Проверка: запросы к API модели идут через ваш бэкенд. Ключ в браузере = чужие траты
с вашего счёта.

**SEC-61 · Учтён prompt injection** — P2
Проверка: пользовательский текст и содержимое внешних страниц/файлов не смешиваются
с инструкциями как равные; инструменты, доступные модели, ограничены необходимым; действия
с побочными эффектами требуют подтверждения человека.
Ловушка: «мы написали в системном промпте не выполнять инструкции из текста» — это не защита,
а пожелание. Защита — границы прав и подтверждения.

**SEC-62 · Вывод модели не доверяется** — P1
Проверка: результат не исполняется как код, не подставляется в SQL/шелл, не рендерится
как HTML без санитизации, ссылки из ответа не открываются автоматически.

**SEC-63 · Лимиты на стоимость запроса** — P2
Проверка: ограничение длины ввода и вывода, потолок токенов, квота на пользователя
(см. SEC-38).
