# Что значит чек-лист в конкретном стеке

Определи стек **до** обхода. Пункт, неприменимый к стеку, помечай `н/п` с объяснением —
не выдумывай для него проверку и не молчи о нём.

---

## Supabase

Ключевое: анонимный (`anon`) ключ **должен** быть во фронте, он публичный по замыслу.
Вся безопасность держится на RLS. Без RLS публичный ключ = полный доступ к базе.

- `SEC-18` — главный пункт стека. Для каждой таблицы: RLS включён + есть политики на
  `select/insert/update/delete`. Читай SQL политик, а не галочку в дашборде.
  Типичная дыра: `using (true)` или `with check (true)`.
- `SEC-19` — `service_role` ключ обходит RLS полностью. Он допустим **только** в серверном
  коде (Edge Functions, свой бэкенд). Грепни фронт и бандл.
- `SEC-21` — Storage: политики бакетов отдельно от табличных. Проверь оба.
- Проверь `auth.uid()` в политиках — сравнение должно быть с колонкой владельца, а не
  с чем попало.
- Активная проверка (с разрешения): запрос анонимным ключом к таблице с чужими данными.

## Firebase / Firestore

- `SEC-18` → Security Rules. Правило `allow read, write: if true;` или `if request.auth != null`
  без проверки владельца — открытая база: любой залогиненный видит всё.
- Конфиг Firebase во фронте — нормально и не является утечкой. Admin SDK во фронте — P1.
- Проверь Storage Rules отдельно от Firestore Rules.
- Cloud Functions: проверка аутентификации внутри функции, не только в клиенте.

## Next.js (App Router) / Vercel

- `SEC-08` — `middleware.ts` **не** покрывает всё: route handlers, server actions,
  статически сгенерированные страницы. Проверка прав нужна в каждом обработчике и в каждом
  server action (это публичные HTTP-эндпоинты, а не «внутренние функции»).
- `SEC-04` — всё с `NEXT_PUBLIC_` уходит в браузер. Проверь `.next/static` грепом.
- Серверные компоненты могут случайно передать секрет в клиентский пропс — смотри границы
  `"use client"`.
- Заголовки и CSP — в `next.config.js`, проверь, что они реально отдаются в проде.

## Node / Express

- `SEC-35` — `cors()` без опций разрешает всё. Нужен явный `origin`.
- `SEC-56` — для проверки подписи вебхука нужен `express.raw()` **до** `express.json()`.
- `helmet` закрывает `SEC-34` в один приём, но не CSP по умолчанию в нужном виде.
- Проверь глобальный обработчик ошибок: он не должен отдавать `err.stack` клиенту.

## Django / Rails / Laravel

- `DEBUG = False`, `ALLOWED_HOSTS`/`SECRET_KEY` из окружения — `SEC-43`, `SEC-05`.
- ORM закрывает `SEC-22` кроме `raw()/extra()/execute()` и `ActiveRecord` с интерполяцией.
- CSRF включён по умолчанию — проверь, что его не отключили для API «чтобы работало».
- `SEC-17`: `Model(**request.data)`, `permit!` в Rails, `$request->all()` — массовое присвоение.
- Админка (`/admin`) — `SEC-51`: закрыта, на нестандартном пути, с 2FA.

## Статический сайт / конструктор (Tilda, Webflow, WordPress)

- Большая часть серверных пунктов — `н/п`, и это нормально: писать их как ✅ нельзя.
- Остаётся: `SEC-32/33/34` (заголовки — насколько позволяет платформа), `SEC-37/40`
  (спам на формах), `SEC-42` (куда уходят заявки и кто их видит), `SEC-47` (плагины
  WordPress — основной вектор), `SEC-50/51` (демо-контент, `/wp-admin`, XML-RPC),
  `SEC-52` (бэкапы).
- WordPress отдельно: плагины и темы обновлены, нет заброшенных, у пользователей минимальные
  роли, файловый редактор в админке отключён.

## Мобильное приложение с бэкендом

- Всё, что в приложении, — публично: ключи в бинарнике извлекаются. Секреты только на сервере.
- Certificate pinning — не замена серверной авторизации.
- Проверки только в приложении обходятся полностью: клиент — не граница доверия.
