# Pipeline: Flutter-приложение от идеи до проверенного кода

Сегодня: !`date +%F`. **Все даты в артефактах берёшь отсюда**, а не по памяти —
своей текущей даты ты не знаешь.

Десять стадий с **жёсткими воротами** между ними. Ты ведёшь пользователя по стадиям,
материализуя каждую в файл. Файлы — единственный источник правды: контекст сессии
умирает, `docs/pipeline/` живёт.

Стек — Flutter/Dart. Код, тесты, примеры и команды в артефактах — под него.
Архитектура, структура папок, обязательные пакеты, генерация и тестовые пакеты —
в `references/architecture.md`. **Это закон:** читай его перед стадиями 2–8 и следуй ему.
Отступление — только по решению пользователя, с записью в `decisions.md`.

```
0. context load    — project brief подгружается, не пересказывается
1. idea            — что и зачем, в 3–5 предложениях
2. plan + criteria — шаги + явное «готово = ...»
3. risk spikes     — только реально неизвестное, код на выброс
4. contracts       — модели, сигнатуры, состояния, формат ошибок
5. vertical slice  — один сквозной путь end-to-end
6. tasks           — атомарные, у каждой свой критерий готовности
7. implementation  — по одной задаче за сессию, по TDD
8. audit           — в свежем контексте: тесты + список ручных проверок
9. feedback        — находки аудита → обратно в brief + decision log
```

Стадии 0–9 — цикл разработки, он повторяется. Выкат и деплой в пайплайн не входят.

## Две фазы

Приложение строится в две фазы, каждая проходит стадии 2–9 своим кругом:

| Фаза | Что строим | Данные |
|---|---|---|
| **1 — UI** | фундамент, затем все экраны: адаптивные, отзывчивые, на всех трёх платформах | фейковые репозитории с захардкоженными данными |
| **2 — бэкенд** | Dio, Retrofit, Hive, реальные репозитории вместо фейков | реальный API |

Граница между фазами — **интерфейсы репозиториев**. В фазе 1 они фиксируются
в контрактах, Cubit и экраны работают через них с фейковой реализацией. В фазе 2
пишется реальная реализация тех же интерфейсов, а Cubit и экраны не меняются.
Пришлось менять интерфейс — это решение, его в `decisions.md`.

Фаза 2 начинается, только когда пользователь принял UI фазы 1, — со стадии 2.
Стадия 1 (idea) общая: brief пишется один раз, в фазе 2 он дополняется фактами про API.

## Сначала фундамент, потом функционал

Первый шаг плана фазы 1 — **фундамент**. Собирается он в слайсе (стадия 5), до любого
экрана, в этом порядке:
тема → навигация → локализация → DI → логи. Ни одного экрана с функционалом,
пока фундамент не собран и не проверен пользователем — в том числе внутри слайса
(стадия 5): сначала фундамент и его ручная проверка, потом экран. Экран, написанный до темы
и локализации, потом переписывается целиком: захардкоженные цвета, строки и переходы
расползаются по всему коду. Как устроен каждый элемент фундамента — в `architecture.md`.

## Артефакты

Всё в `docs/pipeline/` в корне проекта:

| Файл | Стадия | Природа |
|---|---|---|
| `state.md` | все | текущая стадия + статус ворот. Обновляй **каждый** раз |
| `brief.md` | 1, 5, 9 | живой документ: что строим, зачем, ограничения, стек, как запускать |
| `plan.md` | 2 | шаги + acceptance criteria (проверяемые) |
| `spikes/` | 3 | код на выброс + `spikes/FINDINGS.md` с ответами |
| `contracts.md` | 4 | модели данных, сигнатуры, состояния, конфиг, ошибки |
| `tasks.md` | 6 | атомарные задачи с DoD-чекбоксами |
| `audit.md` | 8 | отчёт аудита свежим контекстом |
| `decisions.md` | 9 (append) | лог решений: дата, решение, альтернативы, почему |

`plan.md`, `contracts.md`, `tasks.md` и `audit.md` делятся на разделы по фазам.
`docs/pipeline/` **в git не хранится.** Создавая папку, сверь `.gitignore` проекта
с шаблоном из `architecture.md` (раздел «.gitignore»): недостающие строки добавь
и скажи об этом пользователю одной строкой.

Шаблоны — в `references/templates.md`. Детали по стадиям — в `references/stages.md`.
Архитектура и пакеты — в `references/architecture.md`.
Читай нужный раздел `stages.md` **перед** началом стадии, а не по памяти.

## Правило ворот (нарушать нельзя)

В конце каждой стадии:
1. Запиши артефакт на диск.
2. Обнови `state.md`.
3. Покажи **сжатую** сводку: суть + что решили. Не пересказ файла.
4. Задай явный вопрос про переход и **остановись**. Следующую стадию не начинаешь,
   пока пользователь не сказал «да / дальше / поехали».

Исключение: пользователь явно сказал «не спрашивай, гони до конца». Тогда идёшь подряд,
но артефакты всё равно пишешь и в конце показываешь их список. Ручную проверку
(см. ниже) это исключение не отменяет: её результат всё равно нужен от пользователя.

## Ручная проверка пользователем

Работу функционала и UI подтверждает **пользователь своими руками**, а не твой вывод
в консоль. Ты не можешь увидеть экран так, как его видит человек, поэтому «отработало»
от тебя не доказательство.

Везде, где нужно показать, что функционал работает (стадии 5, 7, 8), ты сам прогоняешь
автотесты и `flutter analyze`, а затем даёшь пользователю блок:

```
Проверь сам — T-05 «Отметка привычки»
Платформы: iOS — flutter run -d <iPhone>
           Android — flutter run -d <эмулятор>
           Web — flutter run -d chrome
Шаги:      1. На главном экране нажми чекбокс у «Бег».
           2. Web: сузь окно до ширины телефона и растяни на весь экран.
Ожидаемо:  чекбокс отмечен сразу после нажатия, серия выросла на 1.
UI:        на узком окне — список в одну колонку, на широком — сетка; шапка
           на жидком стекле, контент под ней прокручивается; в тёмной теме фон нейтральный.
```

Платформы — **все три**, если задача не ограничена одной явно. Шаги — конкретными
действиями, ожидаемое — наблюдаемым результатом, отдельной строкой — на что смотреть в UI:
адаптивность (узкий и широкий экран), отзывчивость (реакция на нажатие, загрузка),
светлая и тёмная тема. Задача или стадия закрыта только после ответа пользователя
«проверил, работает». Нашёл расхождение — это дефект в текущей задаче, а не новая задача.

## TDD

Разработка ведётся по TDD: **сначала тест, потом код.**

1. **Красный.** Пишешь тест на случай из поля `Тесты` задачи. Запускаешь — он должен упасть,
   и упасть по ожидаемой причине. Тест, который сразу зелёный, ничего не проверяет.
2. **Зелёный.** Минимальный код, чтобы тест прошёл.
3. **Рефакторинг.** Чистишь, тесты остаются зелёными.

Тесты покрывают **основные случаи, без фанатизма**:
- основной сценарий задачи;
- 1–3 важных краевых случая: пусто, ошибка, граница диапазона;
- логику и состояния — юнит-тестами, ключевое поведение экрана — виджет-тестами.

Пакеты (`bloc_test` + `mocktail`) и что тестировать на каждом слое — в `architecture.md`.

Не тестируешь: тривиальные геттеры и конструкторы, поведение самого Flutter,
сгенерированный код, чистую вёрстку и внешний вид — это закрывает ручная проверка.
Процент покрытия — не цель. Тест, который ломается от любого рефакторинга, хуже, чем его отсутствие.

## Секреты

Секреты **никуда не попадают**: ни в код, ни в ассеты, ни в `--dart-define`, ни в git,
ни в `docs/pipeline/`, ни в тестовые данные, логи и сообщения чата.

- Всё, что лежит в сборке приложения, извлекается из неё. Ключ внутри приложения —
  уже не секрет. Если фича требует секрета на клиенте — это вопрос архитектуры:
  стоп, обсуди с пользователем, решение — в `decisions.md`.
- В артефактах секрет упоминается только **именем** и способом получения, никогда значением.
- Файлы со значениями секретов не читаешь и не создаёшь. Нужен — скажи пользователю,
  что положить и куда, он сделает сам.
- Увидел значение секрета в коде, истории или выводе — не повторяй его, сразу скажи
  пользователю: ключ скомпрометирован, его нужно отозвать и перевыпустить.

## Генерируемые файлы

Генерацию **запускаешь ты сам**, не дожидаясь пользователя:
- изменил аннотации (freezed, json, retrofit, injectable, auto_route, hive) —
  `dart run build_runner build --delete-conflicting-outputs`;
- изменил ARB — `flutter gen-l10n`;
- новый проект или спайк-приложение — `flutter create`.

Сгенерированные файлы **не хранятся в git** (шаблон `.gitignore` — в `architecture.md`).
Поэтому в начале сессии, если их нет или они устарели, сначала генерация, потом тесты.

- Сгенерированные файлы руками не правишь и не пишешь вместо генератора.
- Генерация упала — это ошибка в исходнике с аннотациями, чинишь исходник.
- Два `build_runner` одновременно в одном проекте конфликтуют. Субагентов, запущенных
  параллельно, отправляешь с пометкой «без генерации», а генерацию после них запускаешь
  сам один раз.
- В проекте, где сгенерированные файлы уже лежат в git, сам их из индекса не убираешь —
  скажи пользователю, это его решение.

Какие пакеты генерируют код — в `architecture.md`.

## Правило нулевой стадии

`brief.md` **подгружается, не пересказывается.** Прочитал — работай с этим знанием молча.
Пересказ brief пользователю запрещён: он его писал. Максимум — одна строка
«brief загружен: <проект>, стадия N, следующая задача T-xx».

## Старт сессии

1. Есть `docs/pipeline/state.md`? → стадия 0: прочитай `brief.md`, `state.md`, и артефакт
   текущей стадии. Одна строка подтверждения → продолжай с зафиксированной стадии.
2. Нет? → создай `docs/pipeline/` и переходи к стадии 1. В проекте уже есть код —
   работаешь по разделу «Проект, где код уже есть».
3. Пользователь назвал стадию явно («давай контракты», `/pipeline 4`) — прыгай туда, но сначала
   прочитай артефакты предыдущих стадий. Не выдумывай контекст, которого не читал.

**Откуда берётся идея.** Только от пользователя, на стадии 1. Он может дать её сразу
в аргументе (`/pipeline приложение для учёта расходов, дизайн в design/`) — тогда это
стартовая точка для вопросов, а не готовый brief. Аргументов нет — спрашиваешь сам.
Идею не додумываешь: всё, чего пользователь не сказал, — вопрос, а не допущение.

## Дизайн-макет

Пользователь может дать макет (HTML, скриншоты, Figma-экспорт). Режим работы с ним
фиксируется на стадии 1 в `brief.md`, раздел «Дизайн»:

- **Строго** — режим по умолчанию, если пользователь не сказал иначе. Экраны, раскладка,
  цвета, шрифты, отступы — как в макете. Отступление — только с согласия пользователя,
  запись в `decisions.md`. Цвета макета при этом всё равно идут через тему
  (`AppColors` / flex_color_scheme), а не хардкодом.
- **Ориентир** — из макета берутся состав экранов, функционал и навигация между ними.
  Цвета, шрифты и стиль — по ответам пользователя и `architecture.md`, а не по макету.

Макет — источник, а не закон: на любой стадии пользователь может что-то поменять.
Изменение записывается в `decisions.md` и с этого момента важнее макета. При
расхождении макета и `decisions.md` прав `decisions.md`.

Макет читаешь сам (HTML-файлы — инструментом чтения). По разметке не понять, как выглядит
экран, — попроси скриншот. Где макет используется: стадия 2 (экраны и функционал → шаги
плана), стадия 4 (страницы и состояния), стадия 6 (поле `Дизайн:` у задачи — какой файл
макета ей соответствует), ручная проверка в режиме «строго» — сверка с макетом.

## Проект, где код уже есть (brownfield)

Пайплайн написан под чистый лист. В существующем проекте стадии те же, но три из них
работают наоборот — не проектируешь, а **извлекаешь**. Плюс четыре правила ниже.

**Фаза — по изменению**, а не по проекту:
- новая фича — сначала её UI на фейковом репозитории (фаза 1), потом подключение к API (фаза 2);
- чисто UI-правка — только фаза 1;
- работа с существующим API — сразу фаза 2.

**Архитектура.** Новый код пишется по `architecture.md`. Старый код, написанный иначе
(другой state management, нет barrel-файлов и т.п.), **не переделывается** — рефакторинг
под `architecture.md` только по прямой просьбе пользователя, отдельными задачами.
Отступления старого кода один раз фиксируются в `brief.md`, раздел «Отступления от
архитектуры». Новый код, который стыкуется со старым, подстраивается под стык, не ломая его.

**Фундамент.** Проверь, какие из пяти элементов фундамента (тема, навигация, локализация,
DI, логи) уже есть. Недостающие — первые задачи фазы 1, если изменение их требует,
или запись в `decisions.md`, что обходимся без них.

**Базовая точка.** На стадии 0 прогони `flutter analyze` и `flutter test` и запиши
результат в `brief.md` («Базовая точка»: сколько замечаний, какие тесты красные).
Дальше требование — **ноль новых замечаний** и не сломать тесты, которые были зелёными.
Старые замечания и красные тесты чинятся только задачами, не «заодно».

Стадии:

- **1 idea.** Brief пишется по факту: что приложение делает **сейчас**, и отдельным разделом —
  что мы хотим изменить. Не переписывай замысел автора, ты его не знаешь.
- **4 contracts.** Контракты вычитываются из кода: реальные классы, сигнатуры, состояния,
  формат конфига. Расхождение «как написано» и «как задумано» — находка,
  её в `decisions.md`, а не молчаливое «исправление».
- **5 vertical slice.** Слайс уже существует. Вместо написания — прогони имеющиеся тесты
  и дай пользователю ручную проверку сквозного пути. Не работает — это первая задача,
  а не повод идти дальше.

Скоуп при этом сужается до изменения: пайплайн ведём по той части приложения, которую трогаем,
а не по всему репозиторию. Полная инвентаризация чужого кода — отдельная работа,
и её не делают «заодно».

## Стадии (кратко; развёрнуто — в references/stages.md)

**0. Context load.** Повторная сессия: подгрузить brief + state молча. Новый проект:
стадия пустая, окружение проверяет пользователь сам — сразу к стадии 1. Проект, где код
уже есть, первый запуск: базовая точка `flutter analyze` / `flutter test` в brief.

**1. Idea → brief.md.** Вытащи суть вопросами пачкой (AskUserQuestion, не по одному).
Кто пользователь, какую боль решаем, что считается успехом, что явно вне скоупа,
жёсткие ограничения, языки локализации. Платформы фиксированы: iOS, Android, Web.
Если темы ещё нет (новый проект или в старом её нет) — ещё и про вид: есть ли макет
и как ему следовать, основной цвет, шрифты, светлая/тёмная тема.
Итог — 3–5 предложений, подтверждённых пользователем, плюс изученные внешние
зависимости (доки, лицензии, ToS). Кладётся в `brief.md`.

**2. Plan + criteria → plan.md.** План текущей фазы, 3–7 крупных шагов. В фазе 1
первый шаг — фундамент. К каждому — «готово = ...»
в форме «дано → когда → тогда». Критерий проверяй вопросом «как я проверю это,
не спрашивая мнения?». У каждого критерия — чем проверяется: автотест и/или ручная
проверка пользователем. Нет ответа — переписывай. Отдельно — non-goals.

**3. Risk spikes → spikes/.** Только то, чего мы не знаем и что может обрушить план.
В фазе 1 — обычно поведение UI-пакетов на Web, в фазе 2 — поведение API.
Один спайк — один вопрос да/нет + факты. Код в `spikes/` **на выброс**: не рефачить,
прод-код его не импортирует, TDD к нему не применяется. Ответы — в `spikes/FINDINGS.md`.
Спайк убил допущение — возврат на стадию 2, это успех спайка, а не провал.

**4. Contracts → contracts.md.** Модели данных, публичные сигнатуры, состояния экранов,
схемы хранения и ответов, формат конфига, таксономия ошибок. Пиши как Dart-код, не прозой,
по слоям из `architecture.md`. Фаза 1: фичи и маршруты, модели, интерфейсы репозиториев,
freezed-состояния Cubit, брейкпоинты. Фаза 2: Retrofit-API, JSON-модели, Hive, ошибки.
Реализации нет — только формы. Проверка: по контрактам можно написать заглушки и тесты,
и они состыкуются типами. Здесь же — какие секреты и доступы нужны: только имена
и способ получения (см. «Секреты»).

**5. Vertical slice.** Один сквозной путь, реально работающий. Самый узкий из возможных,
всё постороннее захардкожено. Фаза 1: фундамент целиком (с ручной проверкой) + один
экран через Cubit из DI на фейковом репозитории, адаптивный, на трёх платформах. Фаза 2: один реальный запрос
к API через репозиторий до экрана. Основной путь закрыт тестом, затем — ручная проверка
пользователем. Стадия не закрыта, пока пользователь не подтвердил, что слайс работает.
Сразу после — впиши в `brief.md` раздел «Как запускать» теми командами, которые
только что сработали. Дальше по ним работают и будущие сессии, и аудитор на стадии 8.

**6. Tasks → tasks.md.** Атомарные: одна задача по объёму = один осмысленный коммит.
У каждой — файлы, что делаем, тесты, ручная проверка, зависимости, нужна ли генерация.
**DoD задачи** = тесты из поля `Тесты` зелёные + `flutter analyze` чистый + ручная
проверка подтверждена пользователем.
Порядок в файле = порядок выполнения. Мелкие задачи одного экрана можно объединить
в **пачку** с одной общей ручной проверкой (см. стадию 7).

**7. Implementation.** **По одной задаче за сессию, по TDD.** Тест → красный → код →
зелёный → рефакторинг → `flutter analyze` чистый → блок «Проверь сам» → подтверждение
пользователя → `[x]` → отчёт в 1–3 строки → остановился и спросил.
Задача разрослась — стоп, дроби в `tasks.md`, потом делай.
**Пачка** — исключение из «одной задачи за сессию»: задачи пачки делаются подряд,
каждая по TDD, а ручная проверка одна — на всю пачку в конце.

**Правило трёх попыток.** DoD не сходится после трёх заходов — прекрати чинить.
Это не задача не решается, это задача поставлена неверно: не хватает знания (→ спайк,
стадия 3), неверен контракт (→ стадия 4) или DoD непроверяем (→ стадия 6). Доложи
пользователю, что перепробовал и какой из трёх случаев видишь. Четвёртая попытка тем же
способом — самый дорогой способ потратить сессию.

**8. Audit → audit.md.** Субагент `pipeline-auditor` со свежим контекстом.
Он не видел, как писался код, — в этом смысл. Прогоняет тесты и анализатор, сверяет
код с контрактами и составляет список ручных проверок по каждому AC. Ручные проверки
проходит пользователь. Промпт — по шаблону из `references/stages.md`. Сам аудит не проводишь.

**9. Feedback.** Находки аудита и ручных проверок → обратно в `brief.md` (привести
к тому, что построено) и в `decisions.md` (append-only, абсолютные даты).
Оставшиеся дефекты — задачами в `tasks.md`. Дальше: остались задачи или дефекты
текущей фазы — следующий проход со стадии 7. Фаза 1 закрыта и UI принят — фаза 2
со стадии 2.

## Роутинг: кто выполняет стадию

Модель главного цикла переключить изнутри нельзя — её задаёт пользователь через `/model`.
Поэтому роутинг устроен так: **мышление остаётся в главном цикле, рутина уходит
субагентам, у которых модель прибита в их определении.** Имена моделей живут там,
а не здесь: скилл говорит про роли и переживает смену поколений моделей.

| Стадия | Кто выполняет | Почему |
|---|---|---|
| 0 context load | главный цикл | дёшево, чтение пары файлов |
| 1 idea | главный цикл | диалог с пользователем, делегировать нечего |
| 2 plan + criteria | главный цикл, сильная модель | здесь решается судьба проекта |
| 3 risk spikes | субагент `pipeline-spike` | замкнутая механика: скрипт → запуск → факты |
| 4 contracts | главный цикл, сильная модель | архитектура; ошибка тут стоит дороже всего |
| 5 vertical slice | главный цикл | проверяем контракты собой, не чужими руками |
| 6 tasks | главный цикл | разбиение требует всей картины |
| 7 implementation | по типу задачи, см. ниже | |
| 8 audit | субагент `pipeline-auditor` | нужен свежий контекст, а не дешёвая модель |
| 9 feedback | главный цикл | |

**Стадия 7 — исполнитель задачи решается на стадии 6, не на бегу.** У каждой задачи
в `tasks.md` проставляй поле `Исполнитель:`:

- `субагент` — рутина: модели, Retrofit-клиенты и репозитории по готовому контракту,
  тесты по готовому контракту, механические правки. Отдаёшь субагенту `pipeline-task`.
- `главный цикл` — задача трогает архитектуру, требует решений или диалога с пользователем.
  Делаешь сам. **Если сомневаешься — главный цикл**: делегирование не бесплатно,
  субагент заново поднимает контекст, и на неоднозначной задаче это дороже, чем сделать самому.

Ручную проверку пользователю всегда даёшь ты, а не субагент.

Что сказать пользователю про его сторону: на стадиях 2 и 4 держать самую сильную доступную
модель, на 7 при серии рутинных задач — можно переключиться на быструю. Актуальные имена он видит
в `/model`, там же есть комбинированные режимы «планирование сильной, исполнение быстрой».
Говори это **один раз на воротах** нужной стадии, не напоминай каждое сообщение.

## Стиль кода — действует на всех стадиях

### Комментарии

Комментарий объясняет **почему**, а не **что**. Что делает код — видно из кода.

Пиши комментарий, только если он несёт знание, которого в коде нет:
- неочевидное внешнее ограничение («API отдаёт `price` строкой с пробелами-разделителями,
  `int.parse` на ней падает — чистим сами»)
- причина обходного пути и что сломается без него
- откуда взялось магическое значение (ссылка на спайк, тикет, замер)
- намеренный отказ от очевидного решения и его причина

**Не пиши никогда:**
```dart
// Увеличиваем счётчик на единицу
counter++;

// Виджет списка привычек
class HabitList extends StatelessWidget {

// ---------- ХЕЛПЕРЫ ----------
```
Это шум: он повторяет код, устаревает первым и приучает не читать сам код.
Doc-комментарии `///` — только там, где неочевидны контракт, единицы измерения или
побочные эффекты. Тривиальному методу `///` не нужен. **Doc-комментарий, пересказывающий
имя (`/// Количество дней в серии` над `streakDays`), — чистый шум.**

**Измеримые ориентиры** (словесного «подгоняй под окружающий код» на практике не хватает):

- Комментариев в файле — примерно **5–8% от строк кода**. Выше 12% — почти наверняка
  объяснение самого себя, а не кода.
- **Над одиночным вызовом — не больше одной строки комментария.** Три строки обоснования
  над одной строкой кода — это сообщение коммита, а не комментарий.
- Разброс плотности между файлами одного проекта — признак поломки. Если в одном модуле
  25%, а в другом 3%, значит, комментировался ход мыслей: гуще там, где дольше думал.

Проверяй себя вопросом: **«это знание или мой мыслительный процесс?»** Про чужой API,
про грабли, про причину неочевидного выбора — знание, оставляй. Про то, как ты пришёл
к решению, — процесс, выкидывай.

**Не объясняй отсутствие.** «Кэша здесь нет», «здесь намеренно нет ретрая» —
бесконечный жанр: к любой строке можно дописать, чего в ней нет. Комментируй то, что
есть. Исключение — если отсутствие выглядит как забытое и кто-то полезет «чинить».

**Не пересказывай общеизвестное.** «`const`, чтобы виджет не пересобирался»,
«`dispose`, чтобы не было утечки» — это знает всякий, кто пишет на Flutter.
Правило действует и вне кода: `pubspec.yaml`, `analysis_options.yaml`, конфиги — там та же норма.

В файле без комментариев не начинай их расставлять.

### Dart

- **Dot shorthands — всегда**, где тип выводится из контекста: `.center`, `.transparency`,
  `.all(16)`, а не `MainAxisAlignment.center`, `MaterialType.transparency`,
  `EdgeInsets.all(16)`. Требует Dart 3.10+.
- **Один файл — один класс.** Виджет, Cubit, репозиторий, его фейк, клиент API — каждый
  в своём файле, имя файла — имя класса в snake_case. Исключения:
  - состояния Cubit — все в одном файле (`<name>_state.dart`);
  - модели фичи — можно в одном файле, если их немного и они мелкие;
  - приватные вспомогательные виджеты (`_Header`), которые используются только в этом файле.

### Git

- **Не указывай себя в авторах или контрибьюторах.** Никаких `Co-Authored-By`,
  `Generated with`, упоминаний модели в теле коммита или PR. Автор — пользователь.
- Сообщение коммита — о сути изменения, в стиле, уже принятом в репозитории
  (посмотри `git log`, прежде чем писать первый коммит).
- **Коммитишь и пушишь только по явной просьбе.** «Одна задача = один коммит» из стадии 6 —
  это мера **размера** задачи, а не разрешение коммитить самому: задача должна быть такой,
  чтобы её изменения складывались в один осмысленный коммит.
- Закрыв задачу на стадии 7, в отчёте одной строкой предложи готовое сообщение коммита.
  Пользователь коммитит сам или говорит «коммить». Молчание — не согласие.
- Перед первым коммитом проверь, что в индекс не попали файлы с секретами, ключи,
  мусор сборки (`build/`, `.dart_tool/`), **сгенерированные файлы** и `docs/pipeline/`. Секрет, попавший в историю, чистится
  ротацией ключа, а не `git rm`.

## Как себя вести внутри стадии

- **Не забегай вперёд.** На контрактах не пиши реализацию, на плане не пиши контракты.
  Самая частая поломка пайплайна — «я тут заодно уже накидал».
- **Не выдумывай факты.** Не знаешь, как ведёт себя внешний сервис, пакет или платформа —
  это спайк (стадия 3) или веб-поиск, а не догадка в brief.
- **Решения фиксируй сразу** черновой строкой, на стадии 9 соберёшь в `decisions.md`.
- **Артефакты — на языке пользователя**, код и идентификаторы — по-английски.
